# Taste Learnings
- User does ML model work (e.g., YOLO training) in Jupyter notebooks under `notebooks/` (project has a pre-made `notebooks/model.ipynb`); when asked for model/training code, deliver it into the named notebook, not only a `.py` script. Confidence: 0.6
- User wants training/inference run on the GPU — machine has an RTX 2060 SUPER (driver 610.88, covers CUDA 13.x); always pass `device=0`/CUDA when running jobs, don't default to CPU. Confidence: 0.9
- Project venv lives at `.venv/` (Python 3.14, cp314) and is invoked as `.venv/Scripts/python.exe` on Windows — always use that interpreter for running scripts/diagnostics, not bare `python`. PyTorch CUDA wheels only exist in the `cu130` index (`cu128` tops out at torch 2.11.0), so CUDA torch installs must pin the version and use `--index-url https://download.pytorch.org/whl/cu130` (e.g. `torch==2.14.1+cu130`). Confidence: 0.85
- Prefers a structured ML project layout with explicit artifact locations: raw datasets under `data/raw`, dataset YAMLs in `configs/data`, pretrained weights in `models/pretrained`, and final checkpoints versioned under `models/trained/<run_name>/best.pt`; training scripts should download the data, write the config, train, and copy the best checkpoint automatically. Confidence: 0.7
- Background shell tasks in this environment get killed (Ctrl+C, exit 0xC000013A) when the assistant waits on their output; to capture live startup output of long-running jobs (e.g., training), run them in the foreground with a long timeout instead of background+wait. Confidence: 0.6
- Verify fixes by writing diagnostic/test scripts into the session scratchpad and running them with the venv interpreter: test logic against synthetic fixtures first, then a real end-to-end run (e.g., start training, let it be killed mid-run to produce a genuinely resumable checkpoint, then exercise `--resume`) before declaring the fix done. For resume fixes, proof = `results.csv` epochs appended in the SAME run directory plus ultralytics' "Resuming training ... from epoch N" log line. Confidence: 0.8
- User reports bugs in terse, action-only messages (e.g., "it didnt resume training from last checkpoint fix this") with no pleasantries or detail; investigate and fix directly without asking for clarification first. Confidence: 0.6
- File edits in this environment may be reverted or changed externally between an edit and a later run (a fixed script was found back at its original version mid-session); before debugging import/module errors, re-read the file on disk and confirm the module actually exposes the new symbols, and consider a stale `__pycache__`. Confidence: 0.6
- For training scripts, user expects resume to be the DEFAULT behavior — running the script with no flags should auto-resume the interrupted run, not start a fresh one (they were surprised a plain `python train_detector.py` created a new run from scratch); opt-in flag (e.g. `--fresh`) should be what forces a new run. Confidence: 0.85
- When several interrupted runs have resumable checkpoints, the user expects the one with the MOST progress (highest epoch) to be resumed, not the newest directory — e.g. a run at epoch 2 wins over an accidental 1-epoch run. Confidence: 0.75
